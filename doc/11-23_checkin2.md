Read Processing
At the last check-in, we reported that we had successfully aligned our identified fastq using `bwa mem`. We then continued to look through and understand the pairtools software, creating batch scripts to run it on the newly aligned data. There are three processing steps that need to be run with the `pairtools` software: the `parse`, `sort`, and `dedup` functions. The `parse` command extracts micro-c pairs from bams and classifies them, while filtering out low quality alignments. The next step is using the `parse` function to sort the reads by genomic position, which is necessary for removing PCR and optical duplicates with `dedup`. After debugging, we were able to run all of `parse`, `sort`, and `dedup` without errors, however the output of `dedup` did not appear to be correct: the chromosome and locus specifications of different supposed “contacts” were completely nonsensical. Upon closer inspection of the statistics output from the `parse` function, it became clear that something was wrong as there was an extremely low mapping rate and huge amounts of unmapped reads. Looking deeper into the code we found our issue: we had somehow accidentally used the reference genome for Drosophila buskii instead of Drosophila melanogaster. Luckily this should be a quick fix as all of the scripts ([here](https://github.com/gpmoorhead1/Fly_Genome_Architecture/tree/main/analysis/read_processing)) should still work (providing we fix the reference genome), and we should be able to better understand if further things go wrong with our now increased knowledge of QC metrics. 

Binning and Visualization
We had previously been working on the binning and visualization portion of our processing pipeline using a test dataset from the Pairtools documentation website, but it appeared to be very sparse, with only about ~20k contacts. To confirm the suspicion that this was due to our test dataset being particularly small, we went back to the .bam file provided from the documentation and identified that there were only ~40k reads, via samtools view -c MATalpha_R1.bam in terminal. This explains why the heatmap really only looked like a diagonal, since off-diagonal contacts were so sparse as to not appear when looking at the whole map in our RStudio visualization.
	With the RStudio visualization approach, however, we found we had little control over the different parameters of the heatmap. This prompted us to explore a different avenue, using the HiGlass browser tool to explore the contact maps we will generate from our Drosophila data. HiGlass is a browser based tool, but we can run our own instance of it from the terminal using Docker containers (thank you Biology IT for pre-loading Docker onto our department laptops!). A new script, test-higlass.sh contains the Unix commands we ran to create a local instance of HiGlass and upload the same, small .cool test file we had been working with. As noted in the script, the HiGlass browser utilizes multi-resolution .mcool files, meaning it was very slow to uptake a .cool file (since it would need to process it on the fly for zooming in/out across the map), but was quick to uptake a .mcool file for the same dataset that we generated using a cooler command (zoomify). We were already planning to investigate how the .mcool filetype could be useful for our study, since we plan to compare regions of the contact map across different bin sizes/resolutions, so this was a convenient next step.
